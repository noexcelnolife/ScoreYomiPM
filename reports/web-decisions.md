## 1. 決めたこと

### D-W1 公開先は GitHub Pages のプロジェクトサイト、`base href` は `/ScoreYomiPM/`

- 理由: リポジトリ名が `ScoreYomiPM` で、プロジェクトサイトの URL は `/<リポジトリ名>/` 配下になる。
- 帰結: `flutter build web` に `--base-href /ScoreYomiPM/` を渡す必要がある。渡し忘れると
  ローカル（`/` 配下）では動くのに公開先でだけ真っ白になる。**ビルド検証テストはローカル配信だけでは不十分**。
- 対応: 公開用手順を P6 で 1 本のスクリプトにまとめ、`--base-href` を固定する。

### D-W2 レンダラは Flutter 既定（`auto`）を維持し、wasm 版へは切り替えない

- 理由: `skwasm` はスレッド前提の最適化で、GitHub Pages では COOP/COEP を付けられない（Tier B-2）。
  既定の `auto` は CanvasKit にフォールバックし、配信先の制約に依存しない。
- 帰結: `canvaskit.wasm`（約 7.0 MB）が初回 DL に含まれる。削る手段は P6 の課題（§2）。

### D-W3 COOP/COEP は要求しない。OCR もシングルスレッドで動くものだけを採用する

- 理由: GitHub Pages はレスポンスヘッダを設定できない。サービスワーカーで回避する工作は、
  オフライン対応と干渉し、更新時に「古いワーカーが残る」事故を招く。
- 帰結: `SharedArrayBuffer` を使う構成（WASM マルチスレッド）は**採用候補から外す**。
  OCR の処理時間はスレッド 1 本ぶんの制約を受ける。
- 未確認: シングルスレッドでの実測速度（Tier B-3 のレポート待ち）。

### D-W4 画像の保存先は IndexedDB（`IdbBlobStore`）とし、OPFS は採用しない

- 理由: 保存はすでに `BlobStore` 抽象に統一済みで、`dart:io` 実装と差し替えるだけで済む。
  OPFS はブラウザ間の挙動差と同期 API の制約が大きく、得られる利点（大容量）が現状の
  データ量（記録 1 件 200〜500 バイト＋結果画像）に見合わない。
- 帰結: 容量上限はオリジン単位のクォータに従う。上限到達時の扱いは D-W5。

### D-W5 容量は監視しない。書き込み失敗時にだけ知らせる

- 理由: 残量の見積もりはブラウザごとに推定値で、誤差が大きい。「残り 20% で警告」のような
  閾値は、ユーザーに意味の分からない警告を出すだけになる。
- 帰結: 通常時は何も出さない。`QuotaExceededError` を検出したときだけ
  「保存領域の空き容量が足りません。バックアップを書き出したうえで、不要な記録を削除してください。」
  と出す。**この文言が出た時点で、その保存は成立していない。**
- 実装: `BlobStoreQuotaException`（`lib/platform/blob_store.dart`）。

### D-W6 永続化の要求（`navigator.storage.persist()`）は最初の書き込み成功後に 1 回だけ

- 理由: 起動直後に要求すると、利用者にとって目的不明の許可になる。最初の保存は
  「データを残そうと決めた」瞬間なので、文脈が通る。
- 帰結: 初回起動から保存まで到達しない利用者には要求しない。ブラウザが拒否しても保存は続く
  （実測: Chrome は localhost で拒否。設計どおり無視）。

### D-W7 Web では「画像を取り込む」を出さず、「記録を追加」（手入力）を主導線にする

- 理由: 押すと必ず失敗する入口を残さない。手入力画面は既存の `OcrResultScreen` の
  入力なしモードをそのまま使えるため、新規画面を作らない（KISS）。
- 帰結: Web 版は当面「手入力＋バックアップ復元」で記録を増やす。OCR が入るまでの制約として
  ホーム画面に明記する。

### D-W8 収録曲辞書の節は Web では出さない

- 理由: 配信更新も追加 JSON の取り込みも端末のファイルパス前提で、ブラウザに該当する保存先が無い。
- 帰結: 曲名サジェストは同梱シードで動くので検索は成立するが、**辞書の更新はできない**。
  Web での辞書更新は OCR 導入後の課題（IndexedDB 経由の取り込み）。

## 3. 破ってはいけないこと（進め方の制約）

1. `main` へマージしない。push と Release はユーザーの明文許可があるときだけ。
2. 「ビルド検証テスト」と言う（「スモークテスト」は使わない）。
3. `flutter build web` の成功を動作の証拠にしない。判定はブラウザでの観測で行う。
4. 外部送信を前提にしない。OCR モデル・辞書とも自前ホスティング、または同梱で完結させる。
5. 利用者のデータ（記録・画像）を失う経路を作らない。失敗は必ず失敗として伝える。
