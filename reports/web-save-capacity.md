## 1. ブラウザストレージの容量制限（一次情報：MDN）

一次情報: [MDN「Storage quotas and eviction criteria」](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)

ブラウザはオリジン（scheme + hostname + port）単位でストレージを管理する。IndexedDB / Cache API / Origin Private File System (OPFS) はすべて同一のオリジン単位クォータを共有する。

| 技術 | 容量制限 | 備考 |
|:---|:---|:---|
| **IndexedDB** | オリジン単位の動的クォータ（ディスク空き容量の割合） | 固定値なし。ブラウザ・ディスク・ユーザー操作頻度により変動 |
| **Cache API** | IndexedDB と同一クォータを共有 | Service Worker キャッシュ等も含む |
| **Origin Private File System (OPFS)** | IndexedDB と同一クォータを共有 | 大容量バイナリ保存に適する |
| **localStorage / sessionStorage** | 約 5 MiB / オリジン | 文字列のみ。Web 版 OCR や画像保存には不向き |
| **Cookie** | ブラウザによる（通常 4 KB × 数十件） | 本アプリでは使用予定なし |

### ブラウザごとのクォータ計算方式（MDN より）

| ブラウザ | ベストエフェクトモードのクォータ | 持続ストレージ (persistent) |
|:---|:---|:---|
| Chrome / Chromium 系 | ディスク空き容量の割合（グループ上限あり、概ね数 GB〜数十 GB 範囲） | PWA インストール等で自動承認されることがある |
| Firefox | min(ディスクの 10%, 10 GiB グループ) | ユーザーにプロンプト表示 |
| Safari 17+ | ディスク容量の割合（iOS は 1 GB ベース） | ユーザー操作履歴に基づき自動承認/拒否 |
| Safari (旧) | 初期 1 GiB、ユーザー承認で拡張 | ITP により 7 日間未操作で削除されることがある |

> 一次情報より：「データがクォータを超過すると IndexedDB / Cache / OPFS 書き込みで `QuotaExceededError` 例外が発生する」。また「ベストエフェクトストレージはディスク逼迫時にブラウザが LRU（使用頻度低い順）で削除する可能性がある」。

### 容量確認 API（ブラウザ標準）

| API | 戻り値 | 用途 |
|:---|:---|:---|
| `navigator.storage.estimate()` | `{ quota: number, usage: number }`（推定値） | 残容量（`quota - usage`）の把握。書き込み前の事前チェックに使用 |
| `navigator.storage.persisted()` | `Promise<boolean>` | 永続ストレージ移行済みかの確認 |
| `navigator.storage.persist()` | `Promise<boolean>` | 永続ストレージへの移行要求（承認はブラウザ/ユーザー次第） |

> MDN より：「`estimate()` は推定値であり、実測値ではない。クロスオリジンデータはパディングされる可能性がある」。書き込み直前の精密な容量判定には使えない。

## 2. 容量不足時の失敗時の挙動

### 3.1 書き込み失敗（QuotaExceededError）

IndexedDB / Cache API / OPFS でオリジンクォータを超える書き込みを試みた場合、`QuotaExceededError` DOMException がスローされる。トランザクションは中止され、部分的な書き込みはロールバックされる（IndexedDB のトランザクションモデルによる）。

**対応方針**:
- すべての IndexedDB 書き込みを `try/catch` で囲み、`QuotaExceededError` を検知する。
- `UnknownError`（ディスク I/O 問題・プロファイル破損）は容量不足ではないため、別途ハンドリングする。
- 容量不足を検知したら、既存データの削除（古いレコードや画像）を試みるか、ユーザーに ZIP バックアップ＋クリアを促す。

### 3.2 ブラウザによる自動削除（ベストエフェクトストレージ）

ベストエフェクトストレージは、ディスク空き容量不足時にブラウザが**事前通知なしで削除**する可能性がある。削除はオリジン単位で全データ（IndexedDB + Cache + OPFS）をまとめて削除する。

**対応方針**:
- Web 保存を「唯一の保存先」にしない。必ず ZIP バックアップ（エクスポート）の手段を提供する。
- `navigator.storage.persist()` で永続ストレージ移行を試みる。ただし承認はブラウザ/ユーザー次第で、保証されない。
- Safari は 7 日間未操作でデータを削除する可能性がある（ITP）。Web 版では「定期的な ZIP バックアップ」を推奨する文言を UI に入れる。

### 3.3 プライベート閲覧モード（Incognito / InPrivate）

プライベートモードではクォータが小さく、セッション終了時にデータが削除される。Web 版の保存を「一時的」と位置づける。

## 3. 既存アプリデータのサイズ見積もり

### 3.1 譜面データベース（実測）

`app/db/popn_hc_main_v1.json`: **1,026,812 bytes（約 1.0 MB）**（2100 曲）

このファイルは読み取り専用の辞書データであり、Web 版ではアセットとして同梱するか、ネットワーク取得となる。保存データ（IndexedDB）には含まれない想定。

### 3.2 プレイ記録（1 件あたり、構造からの見積もり）

`PlayRecord` の JSON シリアライズサイズ（推定）：

| フィールド | 概算サイズ | 備考 |
|:---|:---|:---|
| id (UUID) | 36 バイト | 固定長 |
| playedAt (ISO8601) | 24 バイト | 固定長 |
| songName | 10〜40 バイト | 曲名による |
| 数値フィールド × 8 (score, cool, great, good, bad, maxCombo, level 等) | 2〜12 バイト/件 | 各値 1〜5 桁 |
| status / source / difficulty / machine | 10〜20 バイト | 列挙値 or 文字列 |
| memo | 0〜200 バイト | 自由文、省略可 |
| resultImagePath | 10〜30 バイト | ファイル名のみ（basename） |
| **1 件あたり合計（推定）** | **約 200〜500 バイト** | メモ長に依存 |

2100 件保存した場合のレコードデータ合計（推定）: **約 400 KB〜1.0 MB**

### 3.3 画像（resultImagePath 参照）

プレイ結果のスクリーンショット画像。1 枚あたりのサイズは**アプリ固有で未実測**（端末・解像度に依存）。目安としてスマートフォンのスクリーンショットは 1 枚 100 KB〜1 MB 程度。

100 件保存時の画像合計（推定）: **約 10 MB〜100 MB**

> 画像サイズは実測が必要。Web 版では IndexedDB に Blob として保存するか、OPFS にファイルとして保存するかを P4b で決定する。

### 3.4 ZIP バックアップ（エクスポート）のサイズ

`backup_export_service.dart` による ZIP には以下を含む：
- `manifest.json`（数 KB）
- `records.csv`（レコード数 × 約 100 バイト）
- 画像ファイル群（resultImagePath 参照）

2100 件 + 画像ありの ZIP は**数 MB〜数十 MB** になる可能性。ZIP 圧縮率は画像形式（PNG/JPG）に依存。

## 4. 残量が少ないときにユーザーへ伝えるべき内容

以下のタイミングで UI に表示するメッセージを定義する。

### 4.1 書き込み前（容量確認時）

`navigator.storage.estimate()` で `quota - usage` が閾値を下回る場合：

> 「保存できる空き容量が少なくなっています。新しい記録を保存できない可能性があります。ZIP バックアップを作成してデータを端点外に保存し、不要な記録を削除することをお勧めします。」

### 4.2 書き込み失敗時（QuotaExceededError）

> 「保存に失敗しました。保存領域の空き容量が不足しています。ZIP バックアップを作成した後、不要な記録や画像を削除してから再度お試しください。」

### 4.3 定期的なバックアップ促し（Safari ITP 等への対応）

> 「このブラウザの保存データは、長期間利用がないと自動的に削除される場合があります。重要な記録は ZIP バックアップで定期的に保存してください。」

### 4.4 プライベート閲覧モード

> 「プライベート閲覧モードでは保存データはセッション終了時に削除されます。通常の閲覧モードでご利用ください。」

## 5. ZIP バックアップを促す閾値の提案

### 5.1 閾値の考え方

| 閾値種別 | 提案値 | 根拠 |
|:---|:---|:---|
| **警告（残り容量）** | 残容率 < 20% または 残容量 < 100 MB | ユーザーに余裕を持って対応させるため |
| **重大警告** | 残容率 < 10% または 残容量 < 50 MB | 書き込み失敗が差し迫っている状態 |
| **ZIP バックアップ強く推奨** | レコード件数 ≥ 500 件 または 画像総サイズ ≥ 10 MB | バックアップなしでデータ喪失リスクが高まる |

### 5.2 実装上の注意

- `navigator.storage.estimate()` は推定値なので、閾値判定は「余裕を持った」値を採用する。
- 実際の書き込み失敗（`QuotaExceededError`）を最終的な判定とし、事前チェックは補助的に使用する。
- 閾値はブラウザ・デバイスにより変動するため、ハードコードせず設定可能にすることを推奨。

### 5.3 ZIP バックアップのタイミング推奨

| タイミング | 文言例 |
|:---|:---|
| 初回保存時 | 「記録をクラウドに同期せずブラウザ内に保存します。データ喪失を防ぐため、定期的に ZIP バックアップをダウンロードしてください。」 |
| 100 件到達時 | 「記録が 100 件に達しました。ZIP バックアップを作成してデータを保護することをお勧めします。」 |
| 容量警告時 | 「保存領域の空きが少なくなっています。ZIP バックアップを作成後、不要な記録を削除してください。」 |
| アプリ終了・スリープ前（可能なら） | 「保存データがあります。ZIP バックアップを作成してから閉じることをお勧めします。」 |

## 6. P4b 実装に向けた推奨方針

| 項目 | 推奨 | 理由 |
|:---|:---|:---|
| ストレージ技術 | IndexedDB（`idb_shim` または同等） | 構造化データ＋Blob（画像）保存に適する。localStorage は 5 MB で不足 |
| 永続化 | `navigator.storage.persist()` を試みる | 承認されれば自動削除から保護される |
| エラーハンドリング | `QuotaExceededError` を `try/catch` で検知し、ユーザー通知 | ブラウザの自動削除も考慮し、読み込み時も「データが存在しない可能性」を想定 |
| バックアップ | ZIP エクスポートを必須機能として提供 | ブラウザ保存は「唯一の保存先」にしない |
| サイズ監視 | `navigator.storage.estimate()` で定期的に残容量を確認 | 書き込み前に余裕を持って警告 |

## 7. リーダーの判断が必要な点

1. **ZIP バックアップ閾値の確定値**: 提案値（残容率 20% / 100 MB 等）を最終決定してほしい。P4b 実装に組み込む。
2. **画像保存先**: IndexedDB Blob か OPFS か。画像サイズが未実測のため、実装前に `app/` の既存画像サイズを実測し、閾値設計に反映する必要がある。
3. **永続ストレージ移行 (`navigator.storage.persist()`)**: 常に要求するか、ユーザー操作後のみ要求するか。
4. **画像サイズ実測の担当者**: 既存アプリの画像ファイルサイズを誰が実測するか。
